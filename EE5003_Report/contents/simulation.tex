\section{Simulation Environment}
\label{sec:simulation}

\subsection{PureEdgeSim Overview}
\label{subsec:simulation-overview}

PureEdgeSim is a discrete-event simulator for cloud, edge, and mist computing built on top of CloudSim Plus \cite{mechalikh2021pureedgesim, pureedgesimgithub, silvafilho2017cloudsimplus}. In the present project, the simulator version is PureEdgeSim 4.2.0 and the underlying cloud engine is CloudSim Plus 6.2.7. PureEdgeSim provides the core event loop, network abstraction, task lifecycle management, and data-center scheduling primitives required for edge-computing research, but it does not natively expose the turn-based multi-agent interaction pattern required by MAPPO.

The implementation used in this report starts from the ML-RL-PureEdgeSim codebase \cite{mlrlpureedgesimgithub}, which already introduced an initial RL-oriented workflow around PureEdgeSim. That earlier code provides a useful starting point for integrating learning algorithms with the simulator runtime, but it does not include the full PRB-aware networking, per-device MARL protocol, or dual-head actor design required for the joint optimization problem studied here. The extensions added in this project are summarized in \Figref{fig:pureedgesim-extensions}.

\subsection{Customized Simulation Environment}
\label{subsec:customized-environment}

Compared with the original PureEdgeSim release and the inherited ML-RL-PureEdgeSim structure, the customized simulator introduces the following seven changes.
\begin{enumerate}[(a)]
    \item \textbf{PRB resource manager.} The default network model is extended with a global PRB pool, fixed reservation for RL-selected PRB actions, and a dynamic allocator for heuristic baselines.
    \item \textbf{Distance-sensitive channel model.} The original simplified bandwidth logic is replaced by the attenuation model in \Eqref{eq:bandwidth-prb}, making wireless quality depend explicitly on transfer distance.
    \item \textbf{RL decision support layer.} The \texttt{DeviceAgentDecisionSupport} module constructs observations, masks infeasible destinations, maps PRB bins to block counts, applies fallback logic, and computes rewards.
    \item \textbf{TCP JSON environment server.} The \texttt{RLEnvServer} class turns the Java simulator into a synchronous MARL environment that exchanges newline-delimited JSON messages with Python policies.
    \item \textbf{Dual execution modes.} The \texttt{AbstractRLManager} class supports both training mode, where Python drives policy updates externally, and offline inference mode, where Java launches a lightweight Python inference server automatically.
    \item \textbf{Unified orchestrator interface.} \texttt{CustomEdgeOrchestrator} dispatches all algorithms through a common orchestration path so that RL and non-RL methods share the same simulation lifecycle.
    \item \textbf{Visualization and diagnostics.} Additional charts were added for MAPPO reward trends, PPO learning curves, destination usage, and PRB-bin selection.
\end{enumerate}

An important design choice is that the simulator remains event-driven rather than being wrapped into a fixed-step game loop. Each agent acts only when a task arrives at the orchestration point. This preserves the temporal realism of the network simulator and avoids introducing artificial synchronization among devices.

\subsection{Simulation Topology and Configuration}
\label{subsec:simulation-configuration}

The network topology and workload definitions were already introduced in \Secref{sec:system-model}. This subsection summarizes the global simulator settings that shape the scale and dynamics of the experiments. The scenario contains 160 devices in a \(200\,\mathrm{m} \times 200\,\mathrm{m}\) area, four edge data centers, and one cloud node. The simulation horizon is 30 minutes, which is sufficiently long to produce tens of thousands of offloading decisions per episode.

\subsection{Task Orchestration Flow}
\label{subsec:task-orchestration-flow}

PureEdgeSim drives the entire system through events. Once a task is generated, it is first sent to the orchestrator, which decides the execution destination and, for RL agents, the PRB level used for the wireless upload. After that, the task is transmitted to the selected destination, executed on the assigned VM, and finally returned to the originating device. \Figref{fig:task-orchestration-flow} shows the high-level flow used in this report.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.92\textwidth]{figures/task_orchestration_flow.png}
    \caption{Event-driven task orchestration flow implemented in the customized simulator.}
    \label{fig:task-orchestration-flow}
\end{figure}

For heuristic baselines, \texttt{CustomEdgeOrchestrator} computes the destination directly. For RL-based algorithms, the same orchestrator delegates the decision to \texttt{MAPPOManager} or \texttt{PPOManager}, which collect the observation, query the Python policy, sanitize the returned action, and push the selected destination and PRB allocation back into the event pipeline. This arrangement ensures that all algorithms are evaluated under the same task generator, mobility model, and data-center configuration.

\subsection{Java-Python Co-Simulation Architecture}
\label{subsec:java-python-cosim}

\subsubsection{Training Mode}

In training mode, Python launches the Java simulator with the environment-server flag enabled. Java creates an \texttt{RLEnvServer} instance and waits for the Python client to connect. The first message is \texttt{marl\_config}, which informs Python about the number of agents, observation dimensions, destination labels, and PRB bins. Thereafter, the interaction proceeds in a repeated request-response cycle:
\begin{align*}
\texttt{marl\_turn\_obs} \rightarrow \texttt{marl\_action} \rightarrow \texttt{marl\_transition},
\end{align*}
followed by \texttt{marl\_episode\_end} at the end of each episode.

This protocol has two advantages. First, the policy code remains in Python, which simplifies neural-network implementation and logging. Second, the simulator remains authoritative for validity checks, fallback handling, timing, and reward calculation.

\subsubsection{Offline Inference Mode}

In offline inference mode, Java automatically launches \texttt{inference\_server.py} and connects to it through the same TCP protocol. The model path is resolved by priority: an explicitly provided checkpoint is used first, otherwise the latest training run is searched, and finally a legacy fallback path is checked. If no model can be loaded successfully, the manager falls back to a safe default action, ensuring that evaluation runs do not terminate because of a missing checkpoint.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.92\textwidth]{figures/java_python_cosim.png}
    \caption{Training-mode and inference-mode data flow in the Java-Python co-simulation architecture.}
    \label{fig:java-python-cosim}
\end{figure}

The same message protocol is reused in both modes, so training and evaluation share a common environment interface. This reduces train-test skew and makes the RL pipeline easier to debug.

\subsection{Baseline Algorithms}
\label{subsec:baseline-algorithms}

The proposed MAPPO method is compared against eleven baselines, including ten heuristic schedulers and one single-policy PPO variant. The heuristics span naive, locality-driven, load-driven, and multi-factor strategies so that the evaluation covers both simple and stronger rule-based references.

\begin{table}[htbp]
    \centering
    \begin{tabular}{p{0.22\linewidth}p{0.68\linewidth}}
        \hline
        \textbf{Algorithm} & \textbf{Decision rule} \\
        \hline
        RANDOM & Randomly select a feasible VM. \\
        LOCAL & Prefer local execution and fall back to edge or cloud through a simple backup rule. \\
        CLOSEST & Choose the nearest edge node, with queue length as the tie-breaker. \\
        EDGE & Restrict execution to the edge tier and choose the least-loaded feasible VM. \\
        CLOUD & Restrict execution to the cloud tier and choose the least-loaded feasible VM. \\
        ROUND\_ROBIN & Select the VM with the smallest task count across all tiers. \\
        TRADE\_OFF & Use a weighted cost proportional to \((tasks+1)\times weight \times taskLength / vmMips\). \\
        INCREASE\_LIFETIME & Favor decisions that preserve device battery lifetime. \\
        LATENCY\_ENERGY\_AWARE & Combine delay and energy terms in a hand-crafted weighted policy. \\
        WEIGHT\_GREEDY & Minimize a normalized weighted sum of distance delay, execution delay, load, and energy. \\
        PPO & Single-policy PPO baseline that removes agent embeddings and shares one actor across all devices. \\
        \hline
    \end{tabular}
    \caption{Baseline algorithms implemented in the customized orchestrator.}
    \label{tab:baseline-algorithms}
\end{table}

The PPO baseline is particularly important because it isolates the contribution of the multi-agent design. Both PPO and MAPPO use the same environment and dual decision heads, but MAPPO introduces agent-specific embeddings and centralized training over a global state. This makes the PPO baseline a closer comparison than a purely heuristic scheduler.
