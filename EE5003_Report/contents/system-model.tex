\section{System Model and Problem Formulation}
\label{sec:system-model}

\subsection{Network Architecture}
\label{subsec:system-architecture}

The target system follows a three-tier LOCAL--EDGE--CLOUD architecture deployed over a \(200\,\mathrm{m} \times 200\,\mathrm{m}\) area. All task-generating devices are treated as edge devices in PureEdgeSim terminology, while edge data centers and the cloud server provide additional remote execution capacity. \Figref{fig:network-topology} illustrates the topology used throughout the experiments.

\begin{figure}[htbp]
    \centering
    \includegraphics[width=0.82\textwidth]{figures/network_topology.png}
    \caption{Three-tier LOCAL--EDGE--CLOUD topology used in the experiments.}
    \label{fig:network-topology}
\end{figure}

Four heterogeneous device classes are configured. Smartphones and sensors generate tasks, while Raspberry Pi nodes and laptops act as background devices that contribute mobility, wireless contention, and compute heterogeneity. The edge tier contains four identical edge data centers placed in the four quadrants of the simulation area at \((50,50)\), \((150,50)\), \((50,150)\), and \((150,150)\). Each edge data center contains two hosts, and each host provides eight virtual machines with \(60{,}000\) MIPS per VM. The cloud tier contains one data center with two hosts and sixteen VMs in total, each VM providing \(150{,}000\) MIPS. The cloud link is abstracted as a fixed-distance wireless hop with an equivalent distance of \(160\,\mathrm{m}\).

\subsection{Task Model}
\label{subsec:task-model}

Three application types are used to generate workloads with different latency and communication characteristics. The rates and workload sizes are defined in \texttt{applications.xml}. In every case, a task may be executed locally, offloaded to one of the edge data centers, or sent to the cloud if the communication and resource constraints permit it.

The task lifecycle in PureEdgeSim proceeds through orchestration, transmission, execution, and result return events. In conceptual form, the life cycle can be summarized as
\begin{align*}
\texttt{SEND\_TO\_ORCH} \rightarrow \texttt{SEND\_TO\_DEST} \rightarrow \texttt{EXECUTE}
\rightarrow \texttt{TRANSFER\_RESULTS} \rightarrow \texttt{FINISHED}.
\end{align*}
Failures occur when task latency exceeds its deadline, communication becomes infeasible due to mobility or coverage, or no valid execution resource can be allocated.

\subsection{Communication Model}
\label{subsec:communication-model}

Wireless communication is modeled at the PRB level. The WLAN bandwidth is \(5000\,\mathrm{Mbps}\), which is discretized into \(5000\) PRB blocks. If a task is assigned \(b\) blocks, the effective bandwidth is given by
\begin{align}
BW = \frac{BW_{\mathrm{WLAN}}}{PRB_{\mathrm{total}}} \times b \times
\min \left(1.0, \left(\frac{d_0}{\max(d, d_0)}\right)^\alpha \right),
\label{eq:bandwidth-prb}
\end{align}
where \(d\) is the transfer distance, \(d_0 = 20\,\mathrm{m}\) is the reference distance, and \(\alpha = 0.5\) is the distance attenuation exponent.

Two PRB allocation modes are supported. For RL-based algorithms, the selected PRB action is converted into a fixed block reservation before transmission begins, and the blocks are released when the upload phase completes. For non-RL algorithms, the requested PRB count is left unset and a dynamic allocator is used. The dynamic allocator builds conflict components over active transfers using breadth-first traversal and then distributes the remaining PRBs according to weighted fairness, where the weight of each transfer is \(1.0 + \texttt{lanPriorityBin}\).

Cloud communication uses the same attenuation equation with a fixed equivalent distance of \(160\,\mathrm{m}\). This preserves a consistent bandwidth model while abstracting long-haul access into a simulator-friendly wireless cost.

\subsection{Computation Model}
\label{subsec:computation-model}

Virtual machines are scheduled with the \texttt{SPACE\_SHARED} policy. Let \(L\) denote the task length in million instructions and \(M\) the MIPS capacity of the assigned VM. The execution time is
\begin{align}
T_{\mathrm{exec}} = \frac{L}{M}.
\label{eq:exec-time}
\end{align}
The destination selector estimates the finish time of every feasible VM and uses this estimate both in the observation features and in the fallback rule applied when an RL action points to an infeasible destination.

\subsection{Energy Model}
\label{subsec:energy-model}

Transmission energy follows the standard radio model
\begin{align}
E_{\mathrm{tx}} = E_{\mathrm{elec}} \cdot bits + E_{\mathrm{amp}} \cdot bits \cdot d^n,
\label{eq:energy-model}
\end{align}
where \(E_{\mathrm{elec}} = 5 \times 10^{-8}\,\mathrm{J/bit}\), \(E_{\mathrm{amp}} = 10^{-11}\,\mathrm{J/bit/m^2}\) in the free-space regime, and \(E_{\mathrm{amp}} = 1.3 \times 10^{-15}\,\mathrm{J/bit/m^4}\) in the multipath regime. To stabilize the reward, the total task energy is normalized by a sliding-window P95 estimator over the most recent 200 samples.

\subsection{Problem Formulation}
\label{subsec:problem-formulation}

The objective is to minimize a weighted system cost that reflects deadline satisfaction, execution efficiency, energy consumption, and wireless resource usage. Because the simulator evolves stochastically with many interacting devices, the problem is modeled as a Dec-POMDP
\begin{align*}
\mathcal{G} = \left\langle \mathcal{N}, \mathcal{S}, \{\mathcal{O}_i\}_{i \in \mathcal{N}},
\{\mathcal{A}_i\}_{i \in \mathcal{N}}, P, R \right\rangle .
\end{align*}

Let \(\pi = \{\pi_i\}_{i \in \mathcal{N}}\) denote the decentralized device policies. For decision step \(t\), define \(F_t \in \{0,1\}\) as the task-failure indicator, \(\widetilde{L}_t\) as the normalized latency ratio, \(\widetilde{E}_t\) as the normalized energy term, and \(\widetilde{B}_t\) as the normalized PRB cost. The long-run optimization target can then be written as
\begin{align}
J(\pi) = \E_{\pi} \left[\frac{1}{T}\sum_{t=1}^{T}
\left(\lambda_f F_t + \lambda_l \widetilde{L}_t + \lambda_e \widetilde{E}_t + \lambda_b \widetilde{B}_t \right)\right].
\label{eq:policy-objective}
\end{align}
In the implemented simulator, this objective is optimized indirectly through the task-level reward
\begin{align}
R_t =
\begin{cases}
-5.0, & \text{if the task fails},\\
5.0 - 2.0\widetilde{L}_t - 0.5\widetilde{E}_t - \widetilde{B}_t, & \text{if the task succeeds},
\end{cases}
\label{eq:implemented-reward}
\end{align}
which is a shaped negative version of the cost in \Eqref{eq:policy-objective}. This reward prioritizes deadline satisfaction first, then lower latency, lower energy, and lighter PRB occupation.

The agent set \(\mathcal{N}\) contains all devices with \texttt{generateTasks=true}, ordered by data-center identifier. The global state \(\mathcal{S}\) is represented by a 27-dimensional vector that summarizes local observations together with aggregate load, energy, task, and PRB statistics. Each local observation \(\mathcal{O}_i\) contains a 13-dimensional device feature vector and an \(N_{\mathrm{dest}} \times 11\) destination-feature matrix. The action space is the Cartesian product of a destination choice and an eight-level PRB choice:
\begin{align*}
\mathcal{A}_i = \mathcal{A}^{\mathrm{dest}}_i \times \mathcal{A}^{\mathrm{prb}}_i.
\end{align*}

The decision process must satisfy the following practical constraints.
\begin{itemize}
    \item The selected destination must be reachable and admitted by the current network state.
    \item The assigned VM must exist and be able to complete the task under the simulator rules.
    \item The global PRB pool must not overflow under fixed RL reservations.
    \item Task latency must remain within the application deadline to be counted as successful.
\end{itemize}

State transitions are not modeled analytically; instead, they are induced by the PureEdgeSim event engine. This makes simulation fidelity higher than in a hand-crafted queueing model, while also motivating the use of reinforcement learning instead of closed-form optimization.
