\subsection{TCP JSON Message Protocol}
\label{subsec:appendix-tcp}

The Java-Python bridge uses newline-delimited JSON over a localhost TCP socket. The message types exchanged by \texttt{RLEnvServer} and the Python client are summarized in \Tabref{tab:tcp-schema}.

\begin{table}[htbp]
    \centering
    \begin{tabular}{p{0.18\linewidth}p{0.15\linewidth}p{0.56\linewidth}}
        \hline
        \textbf{Message type} & \textbf{Direction} & \textbf{Main fields} \\
        \hline
        \texttt{marl\_config} & Java \(\rightarrow\) Python & \texttt{num\_agents}, \texttt{num\_destinations}, \texttt{agent\_obs\_dim}, \texttt{dest\_feat\_dim}, \texttt{state\_dim}, \texttt{prb\_bins}, destination labels, PRB-bin labels \\
        \texttt{marl\_turn\_obs} & Java \(\rightarrow\) Python & \texttt{step\_id}, \texttt{agent\_id}, \texttt{agent\_obs}, \texttt{dest\_features}, \texttt{dest\_mask}, \texttt{state} \\
        \texttt{marl\_action} & Python \(\rightarrow\) Java & \texttt{step\_id}, \texttt{dest\_action}, \texttt{prb\_action} \\
        \texttt{marl\_transition} & Java \(\rightarrow\) Python & \texttt{step\_id}, \texttt{reward}, \texttt{done}, requested and executed destination actions, requested and executed PRB actions, \texttt{dest\_fallback} \\
        \texttt{marl\_episode\_end} & Java \(\rightarrow\) Python & \texttt{done}, \texttt{episode\_index}, \texttt{final\_state}, \texttt{fallback\_count} \\
        \texttt{control} & Python \(\rightarrow\) Java & Control commands such as \texttt{terminate} \\
        \hline
    \end{tabular}
    \caption{TCP JSON protocol used by the co-simulation interface.}
    \label{tab:tcp-schema}
\end{table}

Because the protocol is message-oriented and synchronous, it is straightforward to debug by logging raw JSON lines. This was particularly useful during development of fallback handling and offline inference mode.

\subsection{Hyperparameter Notes}
\label{subsec:appendix-hyperparameters}

The MAPPO and PPO training scripts share the same optimizer-level hyperparameters, including learning rates, clipping factor, minibatch size, and entropy annealing schedule. The main structural difference is that MAPPO uses an agent embedding and a centralized critic over the 27-dimensional state, whereas PPO removes the embedding and relies on a single shared actor representation. Both actors still use the same dual-head action design for destination and PRB selection.

For reproducibility, the final quantitative results reported in \Secref{sec:results} are based on a 40-episode MAPPO training artifact followed by three evaluation seeds: 9001, 9002, and 9003. The currently available PPO comparison artifact is shorter and is therefore discussed only as an auxiliary baseline trend.

\subsection{Reproducibility Notes}
\label{subsec:appendix-reproducibility}

The report is based on the following artifact layout.
\begin{itemize}
    \item The thesis template is stored in the report workspace.
    \item The simulator and learning code are stored in the companion project workspace \texttt{6G\_EdgeCloudComputing\_For\_MAPPO}.
    \item The 40-episode MAPPO training run used for the training curve is preserved under the archived \texttt{40\_30min} directory.
    \item The three-seed MAPPO evaluation summaries are stored as \texttt{run\_summary.json} files under the exported evaluation directory.
    \item Representative heuristic baseline results are currently preserved as dashboard images; rerunning those baselines with consistent CSV export would enable a full quantitative comparison table.
\end{itemize}

In practical use, the workflow is: prepare the PureEdgeSim configuration, launch training mode for MAPPO or PPO through the Python scripts, save model checkpoints, then switch to offline inference mode or batch evaluation mode to collect summary metrics and dashboard plots.
